# Plan Bead

## Workflow

1. Run `workflow_status`. Ensure session context has this `activeBead` and bd status is non-terminal (`in_progress` after claim). If bd status is `inreview`, switch to `review-bead` instead of planning unrelated work.
2. Enter plan mode if not active: `workflow_plan_mode(mode=strict)`, `workflow_plan_mode(mode=auto)` only when explicitly authorized for plan+implement, or `workflow_plan_mode(mode=autopilot)` for autonomous work through code-review/close (`Approved-by: оркестратор`, durable autopilot flag after `plan=off`). `/plan`, `/plan-auto`, and `/plan-autopilot` are optional human UI shortcuts. Do not change `/plan-auto` semantics when using autopilot.
3. Read `bd show <ID>` and `bd comments <ID>` plus relevant files/references.
4. Produce a structured plan. The first `plan_mode_complete({ plan })` after «делай план» / entering plan mode in **strict** opens ready-UI immediately — do **not** dump the draft plan in chat instead of the widget. Ready-UI actions: Исполнить / Остаться / Уточнить / Отправить на plan-review / Задать вопрос. «Задать вопрос» closes the widget without an editor (`discussionOpen=true`); wait for the question in normal chat. «Уточнить» also sets `discussionOpen`. While `discussionOpen` is true, strict `plan_mode_complete` is BLOCKED until Maxim confirms with a whole-message allowlist after trim/lowercase: «да», «ок», «ok», «покажи план», «вопросы закрыты», «можно показывать план» (not a substring inside a longer question). `discussionOpen` resets on plan-mode off→on (`enterPlanMode` when `!wasEnabled`), same moment as the plan-review cycle reset. Questions and «объясни» → chat only; do **not** call `plan_mode_complete` after a clarifying question or while waiting for confirm. `questionnaire` is only for a real A/B choice that cannot continue without a pick — never instead of a paragraph. The plan-review ready button is critique only (same as `/plan-review`): it does not write `PLAN APPROVED` and does not start a supervisor. If the button returns a live finding, the orchestrator immediately calls `record_plan_review_adjudication`; the human does not pick findings; do not ask for «покажи план»; ready-UI is opened by that tool, not by `plan_mode_complete`, until the adjudication is recorded. Dirty plan-review does not set `discussionOpen` and does not wait for a confirm phrase. A chat question while ready-UI is open closes the widget before the answer; that dismiss is not Execute, stay, or plan-review and sets `discussionOpen`. The answer turn must not call `plan_mode_complete` and must not wait for a button. An «Исполнить» click before the answer is visible does not write `PLAN APPROVED` and does not dispatch. Auto/autopilot paths do not use ready-UI.
5. For auto-execute, include the supervisor-dispatch readiness matrix: `PLAN APPROVED`, `Approved-by:`, `Approved-at:`, `Start-commit:` or `START_COMMIT:`, `Files to change:`, `Acceptance:`, `Verification / acceptance checks:`, and implementation intent via either current `Plan:` or legacy `Problem:` + `Approach:`. Canonical gate keys stay English field-lines (`Acceptance:`, not `## Acceptance` and not dual-write `## Приёмка` + `Acceptance:`). Maxim's chat colors Russian `##` via display-only `planMarkdownTransform` in plan-ready UI; `/plan-auto` and `/plan-autopilot` parse the same English canon. Also include the accepted context fields `Problem:`, `Approach:`, `Rejected alternatives:`, `Edge-case review:`, `Worktree / cwd:`, `WORKTREE_LOCK:`, `Risks / rollback:`, `Supervisor:`, and `AUTO_EXECUTE_ALLOWED: true` when applicable. For **new strict plans**, `Supervisor: <agent-name>` is a required dispatch-readiness field (the main-stream supervisor from the Parallel Decomposition Matrix). Canonical form is exactly at the start of the line, no indent or bullet: `Supervisor: test-supervisor`. Autodispatch continuation still omits `agent=`; `dispatch()` reads the field from the latest PLAN APPROVED comment when `agent=` is omitted. Priority: explicit `agent=` > `Supervisor:` > `.pi/supervisor-routing.json` > fail-safe `implementer`. Multi-supervisor plans dispatch explicitly (`agent=` / `spawn_task_workspace`). Missing field keeps the previous table behavior (legacy / Fast Path / consumers). `WORKTREE_LOCK` must name the required task worktree cwd and state that all mutating implementation, tests, bd comments/status updates, git add/commit/push, and typed dispatch/review/docs tools run from that worktree or inside it until explicit `merge-to-main` transitions to `main` after PR merge. If `Worktree / cwd:` names a task worktree, it must already be a readable git worktree on the expected branch before approval; create it first with `bd worktree create <absolute-path> --branch <branch>` rather than raw `git worktree add`.
6. After approval or auto gate, call `workflow_plan_approved(beadId=<ID>, planEvidence=<approved plan text>)`. For autopilot, pass `approvedBy="оркестратор"` (runtime `/plan-autopilot` path does this automatically). This preflights explicit/recorded worktree scope before writing durable `PLAN APPROVED` evidence, then exits plan mode and updates workflow-state in one path; autopilot keeps its session flag after `plan=off`. If it blocks on missing/protected task worktree, the one plan=strict exception is: run the recovery `bd worktree create <absolute-path> --branch <type>/<basename>` from the project checkout (allowlisted; do not `workflow_plan_mode off`), then retry `workflow_plan_approved` with WORKTREE+BRANCH — no second human approval. Do not add `workflow_update`/`setup` to plan-mode tools; prefer create/bind before plan mode when possible. After `PLAN APPROVED`, a nonempty `FAST_PATH_RATIONALE` field-line with autopilot off means no dispatch_supervisor and do not wait for ping — the orchestrator implements directly. After a strict ready-UI «Исполнить», PLAN APPROVED is already recorded and the supervisor is already dispatched; do not call `workflow_plan_approved` again. The typed `workflow_plan_approved` path remains for auto/autopilot `agent_end`, RPC/headless, and strict-recovery. Autopilot must not call `land` or `merge-to-main`.
Approve-path fork for the supervisor handoff (same contract in `dispatch-supervisor`):
- Strict ready-UI execute («Исполнить») without `FAST_PATH_RATIONALE` — the plan-mode runtime already auto-dispatched the supervisor in the same action that wrote `PLAN APPROVED`. Do **not** call `dispatch_supervisor` manually; wait for the supervisor ping (path A). A repeat manual call fails closed with `BLOCKED` «live pane already registered» — an expected idempotent no-op, not a workflow failure. `poll.sh` (path B) stays on-demand insurance only (stall without ping markers / Maxim: «не пинганул»), one poll without a loop, per step 4 of `dispatch-supervisor`; never poll immediately after execute.
- Nonempty `FAST_PATH_RATIONALE` with autopilot off — no supervisor dispatch at all; the orchestrator implements directly (see above; `beads-task-issue-tracker-g1s1`).
- Other non-Fast-Path approve paths without continuation (legacy/RPC-style approval) — manual `dispatch_supervisor` per the `dispatch-supervisor` skill remains the required step.

## Reporting

Chat for Maxim follows `AGENTS.md`. Do not announce normal plan-mode or bd-status values the footer already shows. After approval/auto gate, continue silently unless there is a real decision. After a successful TUI `plan_mode_complete` (overlay/select returned), do **not** write «жду решения» and do **not** require `## Дальше` 1/2/3 about choosing the plan — follow the exclusive next-action in the tool result (`fastPath` → implement now; `dispatched`/`alreadySpawned` → wait for ping, do not `dispatch_supervisor`; `execute-blocked`/`continuation-blocked` → `plan-approval-recovery`). `## Дальше` about the plan only if the widget did not open (`!hasUI` / RPC). For other stops (ambiguity, block, recovery unrelated to a successful TUI complete): `##` + `## Дальше` with `1/2/3`.

## Plan-review cycle cap (workflow_plan_review)

Typed `workflow_plan_review` has **two thresholds** per plan-mode session (counter persists across turns; reset only when plan mode goes off→on / new `/plan`):

1. Auto cap **2** (`MAX_PLAN_REVIEW_CYCLES`) — default against infinite nits (eb4k).
2. Orchestrator extra ceiling **4** (`MAX_PLAN_REVIEW_TOTAL_SPAWNS`) — blocks agent self-loop of `extraCycle` without Maxim.

After auto cap, `extraCycle: true` (default `requestedBy=orchestrator`) allows spawns **3–4** when Maxim asks or residual important/critical remain on a high-risk plan (not Fast Path nits). Cycle **5+** only via `workflow_plan_review({ draftPlan, extraCycle: true, requestedBy: "maxim" })` when Maxim explicitly asked **this turn** — residual-OR does **not** justify cycle 5+. Missing `requestedBy` defaults fail-closed to orchestrator. Extra never returns `CONTINUE`. `/plan-auto` and ready-UI `/plan-review` are separate and not capped/incremented by this counter.

Exclusive stop advice from `planReviewStopAdvice` (risk is telemetry only and never changes advice):

| Condition | Advice |
|---|---|
| `!gateOk` (missing/blocked reviewer or unresolved blockers) | `HARD_BLOCK` |
| `gateOk` and no important/critical findings | `STOP_SHOW_USER` (from cycle ≥ 1; clean APPROVED / minor-only does **not** force a second spawn) |
| `gateOk` and important/critical remain and `cycle < 2` | `CONTINUE` |
| `gateOk` and `cycle >= 2` (includes extra 3–4 and Maxim 5+) | `STOP_SHOW_USER` (show Maxim; extra path never CONTINUE) |

Orchestrator behavior:

- On `CONTINUE`: revise the draft, then call `workflow_plan_review` again.
- On `STOP_SHOW_USER` (auto path, count < 4): present the plan to Maxim. Default auto path stops; do **not** auto-loop. Remaining important/critical findings stay visible. Documented extra path: `workflow_plan_review({ draftPlan, extraCycle: true })` only if Maxim explicitly asks or residual important/critical remain on a high-risk plan (not Fast Path nits). Still call `plan_mode_complete` so ready-UI exists.
- On orchestrator ceiling (cycle ≥ 4): orch extra is forbidden; if Maxim explicitly asked this turn, call `workflow_plan_review({ draftPlan, extraCycle: true, requestedBy: "maxim" })`. Do **not** claim a fifth cycle is impossible for the human. Residual alone does not justify cycle 5+. Reset counter only plan mode off→on.
- After Maxim spawn cycle ≥ 5: still `STOP_SHOW_USER`; same Maxim path for another round if he asks again this turn.
- On `HARD_BLOCK`: do not approve/execute; fix blockers; retry while under auto cap, or with `extraCycle` under orch ceiling / maxim path past it when justified.
- Empty `draftPlan` does not increment the cycle counter (including with `extraCycle` / `requestedBy`).
- Failed spawn still consumes a cycle slot (reserved before `await`), including failed maxim extra.

`classifyPlanReviewRisk` is telemetry only (`low` requires `FAST_PATH_RATIONALE:` plus no `.pi/extensions|skills|agents|rules` / `scripts/` and not both `app/` + `src-tauri`; else `high`). Risk never changes stop advice and never auto-approves. Fast Path extra only if Maxim asked.

## Rules

- Planning mode is read-only, except the single recovery `bd worktree create <absolute-path> --branch <type>/<basename>` when `workflow_plan_approved` blocks on missing/protected task scope; then retry approve with WORKTREE+BRANCH.
- bd status is the lifecycle authority. Do not plan another bead before the current-session active bead has terminal bd status (`closed`, `blocked`, or explicit `deferred`/handoff).
- If requirements or acceptance are ambiguous, ask a single batched question with 2-4 concrete options and stop until answered.
- Plans must preserve self-contained handoff context: problem, approach, rejected alternatives, files, acceptance, and verification evidence.
- Bead/plan `### Verification / acceptance checks` must list only gate-executable or gate-mapped commands (`pnpm test`/`vitest`, `vue-tsc`, `cargo check`, `git diff --name-only`, `git diff --check`, safe `rg`/`grep`). Manual/live/prose checks belong in Acceptance criteria or IMPLEMENTATION evidence, not Verification bullets for `review_bead` matrix.
- Follow-up beads created during planning must use the full `AGENTS.md` template, labels, and known dependencies.
- Decide Fast Path explicitly; risky workflow/policy/review/merge, `.pi/agents`, scripts, or cross-domain work requires approved plan/supervisor path unless a documented exception applies. Plan-review stop advice does not use Fast Path risk to bypass `HARD_BLOCK` or to auto-approve.
- Edge cases are required for non-trivial work.
- Non-trivial plans (anything beyond tiny, low-risk Fast Path work) must include a `Parallel Decomposition Matrix` before approval. For Russian-language beads/plans (default in this project), use human-readable Russian headings: `Поток`, `Цель`, `Агент`, `Зона изменений`, `Зависимости`, `Проверка`, `Решение`, `Причина`. Keep the workflow term `Parallel Decomposition Matrix`. Headings map to technical fields `Stream`, `Goal`, `Agent`, `Write zone`, `Dependencies`, `Verification`, `Decision`, `Reason`: `Поток`/`Цель` selects the work package, `Агент` selects the supervisor type, `Зона изменений` scopes file ownership, `Зависимости` orders streams, `Проверка` defines evidence, `Решение` says `parallel` or `sequential`, and `Причина` explains the routing decision. Do not show English-only column headers to Максим unless he explicitly asks for English.
- Fast Path exception: simple/trivial work may omit the matrix only when the plan includes `FAST_PATH_RATIONALE:` with why direct execution is lower-risk/cheaper than supervisor dispatch, expected touched files/line budget, and focused verification. Workflow/policy/review/merge, `.pi/agents`, scripts, or cross-domain work still requires approved plan/supervisor path unless the exception is explicit.
- Sequential streams are allowed only with one of these reason classes: dependency chain, write conflict, shared verification bottleneck, shared external resource, uncertain scope, or repo/policy limit. Vague reasons such as “files are related”, “same area”, or “related changes” are not accepted. Keep technical values `parallel` / `sequential` and reason-class identifiers in English even when the table headers/content are Russian.

# Установщик Pi workflow

Это инструкция агента, не shell-скрипт. Скилл потом переедет в пакет. Сейчас он лежит в трекере, потому что пакета ещё нет.

Установщик не запускает `pi install`, не создаёт GitHub-репозиторий и не ставит workflow в Haasbot или Hummingbot. Один `install.sh`, который сам пишет настройки, запрещён.

## Как вести человека

Идти по пунктам ниже. На каждом пункте, до записи чего-либо:

1. Посмотреть репозиторий проекта, куда ставят workflow.
2. Предложить вариант словами. Не записывать его сразу.
3. Если человек не понял — объяснить и вернуться к тому же пункту. Не перескакивать.
4. Записать файл только после отдельного «да» на этот пункт.

Сам не угадывать. Спорное спрашивать. Молчаливая подстановка чужого режима запрещена.

Упоминание имени файла настроек не команда записи.

## Файл настроек

Файл настроек проекта — `.pi/config/workflow-chains.json`.

- Писать его можно только после отдельного «да» на пункт, который этот файл меняет.
- Без «да» файл настроек не писать.
- Без «да» не запускать `git init`.
- При обновлении код пакета обновляется, а `.pi/config/workflow-chains.json` не перезаписывается. Перезапись `workflow-chains.json` при обновлении запрещена.
- Проект с другими настройками получает ту же починку кода.
- Закреплённая git-метка сама не переезжает. Новую метку ставят явно.
- Новое поле при отсутствии не ломает проект и не угадывает чужой режим.
- Из установщика охрану не править. Круги ревью — вопросы человеку, не новые поля охраны и не правка кода лимитов.

## Пункты

Каждый пункт — вопрос. Ответ человека важнее рекомендации агента.

### Обновление

Сказать, как устроено обновление, и не делать из этого молчаливую запись:

- код пакета обновляется;
- файл настроек проекта `.pi/config/workflow-chains.json` не перезаписывается;
- проект с другими настройками получает ту же починку кода;
- закреплённая git-метка сама не переезжает, новую метку ставят явно;
- новое поле при отсутствии не ломает проект и не угадывает чужой режим.

### Круги ревью плана

В трекере оставить как сейчас: два автоматических круга и потолок оркестратора четыре. Это описание текущего поведения, не новое поле охраны.

В другом проекте агент рекомендует по стеку. Человек принимает рекомендацию или пишет своё. Не подставлять числа трекера молча.

### Потолок кругов «нашёл дыру, починили, снова ревью»

Потолок таких кругов только для автономного режима. Ручная отправка на ревью без потолка. Не выключать это различие и не записывать его новым полем охраны.

### План по умолчанию

План по умолчанию ждёт человека. Сам идёт до закрытия только если это сказано в первой команде. Не включать автономный проход, потому что так сделано в трекере.

### Кто пишет запись изменения

Вопрос обязателен. Для стратегии не предлагать отдельного писателя как единственный вариант. Человек выбирает, кто пишет запись.

### Готовая работа

Спросить, обязана ли готовая работа попасть в `main` через pull request или достаточно сохранить файл в проекте. Не решать это по ритуалу трекера.

### Нет git

Если git нет, сказать об этом и рекомендовать завести git до установки. Без отдельного «да» не инициализировать репозиторий и не запускать `git init`. Режим beads без git не описывать как рабочий.

### Две дороги в одном проекте

Спрашивать всегда, даже после рекомендации по скану. Скан не закрывает вопрос. Человек говорит, одна дорога в проекте или две. Не угадывать по стеку.

### Cmux

Cmux не спрашивать. Если панелей нет, идти запасным путём через субагентов. Это не остановка и не повод отменить установку.

### Два провала одной и той же проверки

Два провала одной и той же проверки: остановиться и спросить. Это правило везде, не только в трекере. Не чинить третий раз молча.

### Модели

Показать то, что уже настроено в Pi. Спросить, менять ли. Не копировать молча модели трекера.

### Мелкая правка

Мелкая правка без отдельного исполнителя разрешена и в другом проекте. Не запрещать её, потому что проект не трекер.

## Не выключать

Эти правила не выключать ни в трекере, ни в другом проекте:

- не угадывать;
- спорное спрашивать;
- баг механизма не чинить в проекте потребителя — для этого скилл `report-workflow-bug`;
- охрану из установщика не править.

## Чего не делать

- Не писать `.pi/config/workflow-chains.json` и не запускать `git init`, пока на этот пункт нет отдельного «да».
- Не перезаписывать `workflow-chains.json` при обновлении пакета.
- Не добавлять поля охраны под круги ревью и не менять код лимитов.
- Не ставить workflow в Haasbot или Hummingbot из этого скилла и не создавать репозиторий канона.
